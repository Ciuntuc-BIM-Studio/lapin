# lapin-remote 1.0: conformance vectors

The vectors of `docs/spec-lapin-remote.md`. Lapin's tests (C#, `Lapin.Package/Remote`) and Atrium Server's tests (C#, the Atrium repo) both run them; a third implementation should too. They are generated by `make-vectors.mjs` (Node 18 or later, no dependencies):

```sh
node make-vectors.mjs          # writes every file and prints the ids
node make-vectors.mjs --check  # fails when a file on disk is not what the script makes
```

Change the vectors only by changing the script, then run it and commit both. Every file under `blobs/`, `objects/` and `canonical/` is bytes, not text (`.gitattributes`): no final newline is added, no line ending is converted, because the bytes are what is hashed.

## What is here

| Path | What it checks |
|---|---|
| `blobs/<name>` | Nine blobs (empty, ASCII, UTF-8, JSON, binary). An object id is the SHA-256 of these bytes, lowercase hex. |
| `objects/<name>.json` | Four trees (`T1`–`T4`), five commits (`c1`–`c4`, `commit-future`) and two tags (`tag-issue`, `tag-version`), each as its canonical bytes (RFC 8785). An implementation parses each one, re-canonicalises it and gets the same bytes, and hashes the bytes to the id. |
| `canonical/<case>.input.json` → `<case>.expected.json` | JCS itself: key order by UTF-16 code units (the emoji before U+FB33), ECMAScript number output (`1e+21`, `1e-7`, `-0` → `0`, 18 digits rounded), string escaping (only `"`, `\` and controls; `/`, U+2028 and non-ASCII raw; no Unicode normalisation). |
| `ids.json` | Every blob and object with its kind, id and size; the project id of the sessions. |
| `session/push/` | A push, in the order of the spec (§8.1): capabilities, project, refs, objects/missing, PUTs, a resumable upload broken and resumed, refs/update with compare-and-swap (200). |
| `session/push-conflict/` | The concurrent push: a stale `old` gives 409 `ref_moved` with the current value; the client then keeps its work on `refs/heads/wip/…`. |
| `session/fetch/` | A fetch: refs with `If-None-Match` (200, then 304), the commits walk, a pack (its entries listed), one object, a 404. |
| `session/errors/` | 400 `hash_mismatch` (the bad hash), 422 `object_missing` (an incomplete closure), 403, 401, 404 for a non-member, 413, 400 `batch_too_large`, 409 `offset_mismatch`, 422 `tag_immutable`. |
| `folder/fork-detection.json` | The folder remote's append-only ref log: two entries with the same `seq` and `old`, which one wins, what stays reachable. |
| `folder/layout.json` | The files a folder remote holds after the push. |
| `paths/tree-paths.json` | The paths a tree may name (§4.2): valid ones, and refused ones with why (the names that are never parts, `references` among them, compared without case; empty and dot segments; a backslash). |

The objects tell one story: `c1` (tree `T1`: a document and the relations) is on the server; Mihai (owner) commits `c2` (tree `T2`: walls and a script added) and issues it (`tag-issue`, file `issue.pdf`); Ana (editor) committed `c3` on `c1` meanwhile and is refused; `c4` (tree `T4`) names `missing.py`, which is never uploaded. `walls.arrow` and `relations.arrow` stand in for Arrow tables: the protocol never reads a part, so any bytes do.

## The exchanges

Each `session/<name>/NN-<step>.json` is one request and its response:

```json
{
  "step": 4,
  "title": "…",
  "request":  { "method": "POST", "path": "/lapin-remote/1.0/projects/<id>/objects/missing", "headers": { … }, "body": { … } },
  "response": { "status": 200, "headers": { … }, "body": { … } },
  "capture": { "upload": "/response/body/id" },
  "opaque": ["/response/headers/etag"]
}
```

- `path` is relative to the server's root. Header names are lowercase (HTTP does not care); a response may carry more headers than listed.
- The request's body is `body` (JSON), or `bodyFile` (a file relative to the exchange, the raw bytes), with `bodyRange` `{offset, length}` when only part of the file is sent. `bodyNote` describes a body too large to keep.
- The response's body is `body` (JSON; `null`: empty), `bodyFile` (exact bytes), or `bodyZipEntries` (a zip whose entries, in any order and with any compression, have these names and exactly these files' bytes).
- `capture` names a value of a response that later steps use as `{name}` in their paths and bodies (the upload session's id).
- `opaque` lists, as JSON Pointers into the exchange, the values the server chooses (ETags, upload ids, times, the human `message`): a test checks that they are present with the same JSON type, not their value. Everything else is compared exactly; arrays in order.
- The tokens (`Bearer test-access-token-mihai`) stand for whatever the test's server issued to the users of the story: Mihai is `owner`, Ana `editor`, `viewer` a viewer, `stranger` signed in but not a member.
- The steps of one folder run in order against one server, and the folders in the order push, fetch, push-conflict, errors.

A server's test seeds the project with `c1`, `T1`, `document.json` and `relations.arrow` and `refs/heads/main = c1`, plus `issue.pdf` (left by the interrupted push), then replays the sessions. A client's test replays them against a fake server that answers with the responses and checks that the client sends the requests (the order of independent uploads may differ; `objects/missing` may list the same hashes in another order).
