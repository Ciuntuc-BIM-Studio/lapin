## Stage status

Each stage records here what was done, with its decision's source.

**R2 (report #195, 0.1.1667, 1493×802).** The update window is the system dialog of Tauri's dialog plugin, sized by its text; a build's release notes made it taller than the screen, and a system dialog cannot be moved or scrolled by the page. `shortNotes` (`ui/src/app/updates.ts`) now shows at most 10 lines and 700 characters of the notes (a line cut at 160), with an ellipsis when more follows, so the window and its buttons always fit. The Install and Later buttons are unchanged. Test: `updates.test.ts`.

**R3 (report #194, Windows, 0.1.2058).** A view in a window of its own is the same interface in a separate webview (`?pane=`, no ribbon). The section box lives in a zustand store per webview and `syncWindows` shared only the `SHARED` keys of `useUi`, so the box set in the main window never reached the floating view, and the floating window had no ribbon to set one from. `mirrorSectionBox` (`ui/src/app/windows.ts`) now carries the box and its hidden flag between the windows as a `section-box` event (a new window asks the main one at start, as for the other state), and a floating 3D view shows a Section box chip button when it has no box (the existing phrase, no new string). Test: `windows.test.ts`. Not run on a real second window (Tauri events cannot be driven here): check on desktop.
**R5 (forum topic 204), done.** One resolver stays: `Joinery.ClearOpening(spec, lessThreshold)`, called by `OpeningMarkers.Sizes`, which markers, tag symbols, tag rules and the worked-out fields (box tags, labels, schedules, formulas) all read. A new drafting-standards option, `clearHeightLessThreshold` (`standards.options`, one undo step; **Manage → Drafting standards → Project → Door clear height less the threshold**, ticked by default), says whether a door's clear height takes its threshold off: unticked, the Czech rule, the void less the frame only (2050, frame 50 → 2000, whatever the threshold). Only false is stored, so older projects need no upgrade and the default is today's 780/2020 for 900 × 2100, frame 60, threshold 20; a standards file carries it with the options. A window's bottom member stays off either way. The threshold was already modelled (the frame's bottom member, `JoinerySpec.Threshold`, and the detailed threshold across the wall, `JoineryDetails.Threshold`) and sections already cut it; plans never drew it (it lies under the cut). A door type's new `thresholdInPlan` (configurator: **Threshold drawn in plan**) draws it in plan seen from above at LOD 200 and up (`JoinerySymbols.ThresholdPlan`: the detailed threshold across the wall, else the frame's bottom member), in project plans and the configurator's plan; null keeps today's plan. Tests: `ClearOpeningTests` (three new), `drawingOptions.test.ts`. Left: hiding the threshold in sections was not added (sections cut the body as modelled; a door without a threshold is the way to have none), nor a per-type override of the clear-height rule.
**R1, done (26.11.2026; source: the user's roof screenshot, a 45x145 wall plate turned 90°).** A roof's wall plate, ridge beam, purlins and collar ties each take a "laid flat" tick beside their section (`plateFlat`, `ridgeFlat`, `purlinFlat`, `collarFlat`; bool fields shown where the section is, in the roof's properties and the configurator's Framing tab). `Roof.Resolved`'s four section properties return the section as laid (`Roof.Laid`: width and depth swapped), so every use follows from one place: the 3D parts and their names, the cutting list and the timber parts' `Section`, the analytical frames (depth along Z = the laid depth), IFC (members and `Lapin_Timber`; the ticks ride in `Lapin_Intent` and come back on import), quantities and the configurator's preview. A flat plate is lower: `BaseZ` takes its laid depth, so the rafters seat lower by the difference and the planes, ridge and ridge beam come down with them; a flat ridge beam or purlin keeps its top under the rafters. Project styles (`ProjectRoofStyles.Fields`) and user templates (version 2 fields, kept as the roof has them by a template saved before) carry the ticks. Off by default: output unchanged. Tests: `RoofFramingTests` (three new), `roofTemplateLibrary.test.ts`; guide: floors-roofs (EN, RO), the roof-properties scene checks the tick.
**R6: done (26.11.2026; Fabio Emmolo, points 1 and 2).** *Part values as fields.* A placed part's published parameters, derived ones too, are element fields named by their keys, worked out on every ask from the part's table and the object's own values (nothing stored): a platform hook, `DerivedFields.AddNamed` (fields whose names an element's own definition gives, `NamedField`), read by `ParamFormulas.Read` (formulas, schedule columns, filters) after the user's own parameters and before attributes and quantities, by `TagText.Value` (tags and live text, a length in the project's unit), and listed by `FieldCatalog.Across` and `Available` among *Its parameters* in the set `Lapin_PartParameters` (`Lapin_PartParameters.L` when another field has the name); Studio adds them for its classes (`Lapin.Studio/PartFields.cs`). An unpublished parameter is no field. *Part parameters as quantities.* A parameter may carry `measure: length | count | area | volume` (absent: none, as before; refused on a text, a yes/no or an angle, dropped when the kind becomes one; `updatePartParam {changes: {measure}}`, null or `none` clears; shown in `partTree`). A placed part with marked parameters gives the set `AuthoredQuantities.Set` = `Lapin_PartQuantities` (Platform, `Module.cs`) beside its base quantities, each quantity named by its key: schedules read it (`Lapin_PartQuantities.L`), IFC export writes it as that `IfcElementQuantity` (ids stable), and the estimate's articles on the whole element read it first (`Measures.Quantity`, `Parts.Select`: an article by length on a fence of L = 20 m gives 20 m; a count is the marked value, not one per element; a measure the part did not mark reads the body as before). No `IProjectUpgrade`: nothing stored changes, a part without marks measures and exports as before. Interface: the parameter table's **Measure as** column (`measureOptions`, `measureChanges` in `partParamModel.ts`), three new strings in every language. Tests `PartFieldsTests` (3: schedule columns L, derived N, a formula and a text, filters, tags, the pickers; an article per metre and per piece from the marks, defaults unchanged, cleared and undone, refusals; IFC set, stable ids, a package reopened unchanged); `partParamModel.test.ts` grown. Guide: `docs/user/studio-parts.md` (*A part's values in schedules, filters and the estimate*), `schedules.md`, `cost.md` and their Romanian pages. Left: the planning module's productivity norms do not read the marked measures yet (they measure by the element's own quantities); the `studio-part-params` picture needs retaking to show the new column; an article basis by a lowercase key (`h`) is refused by the articles' basis check, so a second marked parameter of the same measure is named by an uppercase key.
**R4 (forum 275), done on `feat/hatch-patterns-edit`.** The cause: the dialog's editor (with its fields, Save and Delete) opens on `hatch.get`, which counts the places naming the pattern by walking every entity's attributes and read each `hatch`, `cutHatch` or `surfaceHatch` value as text; a view style keeps `surfaceHatch` as a switch (`true`), so in a project with a stored view style every `hatch.get` threw, the query's failure was silent and the editor stayed on "Choose a pattern" for every pattern, built-in or the project's (the forum screenshot: YTONG-200X600 highlighted, nothing on the right). Edit and Delete existed but could not be reached. Fixed in `HatchPatternCommands.Walk` (only text values are names; `hatch.usage`, a rename's repointing and a forced delete went through the same code). A second cause, in the dialog, gave the same empty editor in any project: clicking the pattern already selected (the one just made, or the one the dialog opened on) cleared the editor, and since the selection had not changed nothing read it back; the pattern shown clicked again now stays open (`keepsOpen`). The guide's scene met it at once. The dialog now: Duplicate on every pattern with lines or a tile (built in or the project's), opening an unsaved new pattern started from it (NAME-COPY) instead of saving a copy at once; New pattern → Start from (Blank or any pattern); a bin beside each project pattern in the list besides Delete in the editor; a built-in pattern's fields greyed out with a note that it is fixed; a project pattern's note that it is edited in place; "The pattern could not be read." when `hatch.get` fails instead of the empty prompt. A delete in use still asks, falls back as before (materials, standards, sets and rows lose the hatch, drafted hatches take LINES45), keeps every entity (GlobalIds) and is one undo step. No new command (catalogue unchanged). Tests: `PatternEditorTests.A_pattern_is_read_renamed_and_deleted_beside_switches_of_the_same_name` (xUnit), `hatchPatternModel.test.ts` (startFrom, canCopy, canEdit). Guide: `material-graphics.md` (EN, RO) and the scene `matgfx-patterns` (new picture `hatch-patterns-start-from`). Left: the forum reply.
**R7, done (26.11.2026; Fabio Emmolo, point 3).** An article's quantity may be multiplied by the time its element is on site, from the 4D schedule: `ArticleRef.Time` (`time` on a type's article or a material's rule: `auto`, the default and not stored, takes the price's unit's time; `none`; `months`, `workingDays`, `days`, `hours`; anything else refused). Units with a time stop falling back to a count: `MeasureUnits.SplitTime` / `BasisWithTime` read `m × lună`, `m x month`, `cad × mese` (`cad` is now a count), `buc/zi`, `buc/zi lucrătoare`, `100 mp x luna`, `month`, `oră`, `h` as a measure and a time, so `Units.BasisOf` (the estimate's measure and unit factor, the import's "Lapin does not measure" note) measures them; the planning norms' `MeasureUnits.BasisOf` is unchanged but for `cad`, a count there too. Presence is derived on every ask, nothing stored: `ScheduleTimes.Presence` (start of the first leaf task taking the element to the finish of the last) and `Length` (calendar days both ends counted, working days of the calendar with its holidays and exceptions, hours = those days × the calendar's hours a day, now passed as `ScheduleTimes.HoursPerDay`; months = whole calendar months plus the rest over its month's length, 1 March–31 May = 3). `Costing.Compute(q, estimate, times?)` reads the schedule once, only when an article needs it (cost over time, the Gantt's costs and IFC pass theirs). An element no task takes keeps its quantity and the line carries a note ("N element(s) in no task of the schedule…"); no schedule: "The project has no work schedule…"; no Planning module: an article timed only by its unit is priced exactly as before, one set to a duration says the module is missing. The line gives `time`, `duration` ("3 months", or "1.5–3 months" when its elements differ) and `notes` (`cost.estimate`); the estimate and F3 forms (XLSX, PDF, sheets) and the HTML page table append "(× 3 months)" / "(× 3 luni)" and the note; IFC writes `Time` and `Duration` in `Lapin_CostItem`. No `IProjectUpgrade`: nothing stored changes (auto is not written), an old article reads as before; the one visible change for old projects is that a price unit with a time now measures by its measure and, with tasks taking the element, by its duration (what the request asked). No new command (catalogue unchanged; `setArticles` and `setRule`, one undo step each, carry the time). Interface: Map articles gets a **× Duration** column for types and materials (`TIMES`, `articleArg`, remembered with the choice), the estimate line shows "× 3 months" and its notes; nine phrases and two patterns in every language. Tests: `CostDurationTests` (19: the 20 m fence × 3 months = 60 and 80 after the task grows, 10 working days over Romania's Easter, 16 calendar days, 80 and 100 hours, an exception worked, none, no task, no schedule, no Planning module, old articles and units unchanged, one undo step, refusal, a rule's time, unit parsing, months), `estimate.test.ts` (four new). Guide: `cost.md` (*Articles priced by the time on site*, IFC) and `planning.md` (*The cost of the tasks*, *The calendar*), Romanian pages too; the `map-articles` scene checks the new column (the picture needs retaking). Left: the premium `planning-pro` needs no hook (it calls `Costing.Compute(q, est)`, which still compiles; its work statements then see the timed quantities); calendars still know Romania's holidays only (Fabio 6, other countries, left for later); no rounding up to whole months or days (a hire by started month would be a further choice); weeks are not a unit.
