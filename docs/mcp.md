# Lapin and AI agents: the MCP bridge

Every Lapin tool is an engine command with JSON parameters. `scripts/lapin-mcp.mjs` lets an AI agent drive the Lapin that is open, through the Model Context Protocol, on stdio.

The agent's edits go through the same engine as the user's, so:
- they show at once in the window;
- each one is one undo step.

There are **two bridges** (below, *Two bridges: the open project and the CDE*): this one, to the project open in Lapin, and the CDE server's own MCP endpoint, to a project's documents and issues on Atrium Server.

## Setting it up

```sh
claude mcp add lapin -- node /path/to/lapin-pro/scripts/lapin-mcp.mjs
```

The installed desktop app carries a copy of this script (`resources/lapin-mcp.mjs`, copied by `scripts/build-product.mjs`): Help (?) → Connect an AI agent… shows its path and the commands to copy (docs/user/mcp.md). Any MCP client that runs a stdio server works the same way. The bridge needs Node 22 and nothing else.

## Finding the engine

The bridge finds the engine as `lapinbim` does (docs/python.md, How a program finds Lapin): `LAPIN_PORT`, else the host files the engines write while they run (`<user-dir>/hosts/host-<pid>.json` and `<user-dir>/host.json`; stale ones skipped), else the ports 14912–15011 and 47810 probed, each confirmed by its `/health` answering `"engine": "lapin"`. The desktop app's engine is on 14912, a second one on 14913, and so on; `pnpm dev`'s on 47810. The user folder is:
- `~/Library/Application Support/ro.ciuntucbimstudio.lapin` for the desktop app on macOS (`~/.local/share/Lapin` on Linux, `%LOCALAPPDATA%\Lapin` on Windows);
- the repo's `.artifacts/user` under `pnpm dev`.

With one Lapin open the bridge uses it. With several, a call says which are open; set `LAPIN_PORT`, `LAPIN_PROJECT` (a part of the project's path or its file name) or `LAPIN_PRODUCT` in the bridge's environment (`claude mcp add lapin -e LAPIN_PROJECT=House -- node …`). `LAPIN_USER_DIR` reads that folder's host files only.

The engine listens only on 127.0.0.1.

## Tools

| Tool | What it does |
|---|---|
| `lapin_info` | The product, its modules, every command with the arguments it reads, the queries, and the classes with their fields. Call it first. The arguments come from the command catalogue (below), so they never drift; keys read further than it looks are not listed, and the command's error names them. |
| `lapin_model` | The entities (id, class, name, storey, attributes), optionally only some classes. |
| `lapin_execute` | One command, for example `architecture.addWall {x1, y1, x2, y2}`. Lengths are in metres. |
| `lapin_query` | A question that changes nothing, for example `view.drawing`, `schedule.csv`, `civil.elevationAt`, or `core.dependents {id}`: what is built from an element and what it is built from (docs/dependencies.md), to know what an edit changes before making it. |
| `lapin_quantities` | An element's quantity sets. |
| `lapin_documents` | The project's written documents and the templates a new one starts from, in one call. |
| `lapin_document_export` | A document written as DOCX, ODT or PDF to an absolute path on this computer (see Documents). |
| `lapin_export_jg` | The analytical model written as JG Structures' exchange JSON to an absolute path on this computer, with the report of its checks (docs/jg-structures.md). |
| `lapin_undo`, `lapin_redo` | One step back or forward. |
| `lapin_save` | Save the project; the reply lists what the save could not carry over from the file the project was read from (a damaged version part or issued file left out, with a warning), when anything. |

## Replies

Every call is answered `{id, result}` or `{id, error}`; a reply may carry `warnings` beside its result, what went wrong though the call went through: a save (`project.save`, `project.saveBytes`, the version calls) that could not carry something over from the file the project was read from, the recovery journal not written. `lapin_save` lists them. Some results worth knowing in full:

- `coordination.runCheck {kinds?, offset?, clearance?, empty?}` → the clash report `{id, date, hash, stale, clearance, counts, items, unchecked}`: `counts` by kind (`missing`, `held`, `tooSmall`, `empty`, `ok`) and by state (`open`, `fixed`, `ignored`); `items` the numbered clashes; `unchecked` the pairs the run could not check (one of the two has a mesh that is not a closed solid: an element passing through a wall or floor, each `{key, status: "unchecked", mepId, mep, hostId, host, message, …}`), never counted as clear. `coordination.report` gives the stored report, without `unchecked` (a run's own).

## The command catalogue

The arguments each command and query reads are found in the engine's source when Lapin is built (`scripts/command-catalogue.mjs`, regenerated by the Lapin.Protocol build: each handler's `a["key"]`, `P(a, "x", "y")`, and the keys of the helpers it hands its arguments to, with a type guessed from how each is read). The engine embeds the file and serves it as `session.catalogue`, so the bridge has them with an installed app too, where no source is beside it; with an engine from before the catalogue it reads the repo's `engine/src/Platform/Lapin.Protocol/catalogue.json`. The Python package `lapinbim` reads the same catalogue for its typed calls and stubs (docs/python.md), so what is added to a command shows in both.

## Documents

The project's written documents (docs/plan-documents.md) are engine commands and queries like the rest. An assistant makes one this way:

1. `lapin_documents`: the templates (`memoriu-arhitectura`, `caiet-sarcini-finisaje`, `borderou`, and the company's) and the documents there are.
2. `lapin_execute` `document.create {template, name?}`: a document from a template; it returns its `id`.
3. `lapin_query` `document.fields {id}`: what the document can read (every field with its value now, the collections, the tables); `document.preview {id}`: the document filled, with `missing`, the fields the project does not fill yet, and `inputs`, the texts the template asks for.
4. What is missing is written where it lives: the project's data with `lapin_execute` `project.setInfo {client, address, number, phase, designer, …}`; the document's own texts with `document.update {id, inputs: {key: text}}` (a null removes one). `document.update {id, blocks}` replaces the blocks; an image block shows a view (`{kind: "image", view, scale?, width?, caption?}`), cropped to one of its named view boundaries with `boundary` (`LapinViewBoundary`, `view.addBoundary`), as a sheet's viewport bound to it shows it.
5. `lapin_document_export {id, format, path}`: the file written to `path` (absolute; its folders made; a relative path is refused). It returns `{path, bytes, name, missing}`.

A DOCX or ODT exported this way carries its pictures as SVG only: the bridge draws them from `document.images` as the interface does, but has no rasteriser, so the engine puts a blank PNG beside each (Word 2016 and later and LibreOffice show the SVG). A PDF is drawn by the engine whole.

```text
lapin_documents                                         → {templates: [{id: "memoriu-arhitectura", …}], documents: []}
lapin_execute document.create {template: "memoriu-arhitectura", name: "Memoriu"}   → {id: "e41"}
lapin_query   document.preview {id: "e41"}              → {…, missing: ["project.client", …]}
lapin_execute project.setInfo {client: "Ionescu Maria", address: "Str. Florilor 12, Huși"}
lapin_execute document.update {id: "e41", inputs: {situatiaExistenta: "Teren liber, fără construcții."}}
lapin_document_export {id: "e41", format: "docx", path: "/Users/me/Desktop/Memoriu.docx"}
                                                        → {path: "/Users/me/Desktop/Memoriu.docx", bytes: 9461, missing: [...]}
```

`node scripts/lapin-mcp-check.mjs [out-dir]` checks the bridge against an engine of its own on a free port (never the one of `pnpm dev`): it checks that `lapin_info` has the catalogue's arguments, drives the bridge over stdio through this flow, with a picture cropped to a boundary, and checks the PDF, DOCX and ODT it writes.

## Two bridges: the open project and the CDE

An agent can reach two things, each through its own MCP server, and a client can have both at once:

| | The open project | The CDE |
|---|---|---|
| Server | `scripts/lapin-mcp.mjs`, on stdio, on this computer | Atrium Server's `/mcp` (Streamable HTTP), e.g. `https://cde.lapinbim.com/mcp` |
| Reaches | The project open in Lapin: its model, views, documents (this page's tools) | A server project's reference documents (with their files' text), register, containers, publish queue and issues |
| Signs in | Nothing: the engine listens on 127.0.0.1 only | The user's server account, with its project roles: by OAuth in the browser (the client needs only the address), or with a personal access token in the client's configuration |
| Changes | Engine commands, each one undo step the user sees | Through the server's own API, journaled as `via: "mcp"` with the token's or the app's name |

The open project's bridge gets nothing new for the CDE: the engine's `references.*` commands and queries (the project's own reference documents, docs/plan-cde-references.md §3.4) reach it through `lapin_query` and `lapin_execute`, with their arguments from the catalogue (`lapin_info`).

### Setting up the CDE's bridge

There are two ways to sign in. A client that signs in by itself with OAuth (claude.ai's custom connectors, other hosted or desktop clients that follow MCP's authorization specification) needs only the server's address; a client that takes a header (Claude Code, the SDKs, scripts) takes a personal access token.

**By the address (OAuth, stage R6b).** The server must offer `oauth` (its `GET /atrium/1.0/` features).

1. **Add the server by its URL**, `https://cde.lapinbim.com/mcp`. In claude.ai: Settings → Connectors → **Add custom connector**, that URL, no client id or secret. Any other OAuth MCP client: its "add server" with the URL.
2. **The client opens the server's sign-in page** in the browser (it found it from `/mcp`'s 401: the protected resource metadata, then the authorization server's metadata; it registers itself, or names itself by a client ID metadata document). Sign in with the server account's e-mail and password, on the server's own page (check the address bar: `cde.lapinbim.com`); the password never goes to the client.
3. **The consent page** shows the app's name (marked as unverified when the app registered itself and chose it; with the host that publishes it when it names itself by a metadata document), the host the browser goes back to (`claude.ai` for claude.ai; a local address for a client on this computer, with a warning), the account, and what the app may do: **read** (`cde.read`) and, when it asks, **change** (`cde.write`: add and fill reference documents, comment on issues), always with your role in each project. **Allow**, **Allow reading only** or **Deny**.
4. The client gets a token for `/mcp` only (an hour, renewed by a refresh token for 30 days while it is used); the REST APIs do not take it.
5. **Revoke** an app in the same panel as the tokens: **Access tokens…** → **Connected apps** (the app, where it returns to, its access, when it was connected and last used) → the trash button. Its tokens stop at once. Changing the password, or an administrator disabling the account, revokes every app too.

**With a personal access token** (Claude Code, the SDKs, any client that sends a header):

1. **A token.** In the CDE web (signed in on the start screen) or on the desktop (File → Collaborate…, signed in to the server): **Access tokens…** → a name for the client, **Read only** or **Read and write**, an expiry (30 days to a year) → **Make a token**. The token is shown once; copy it then. It goes into the client's configuration and nowhere else, never into a chat, a document or a project: whoever has it works as you on the server until it expires or you revoke it (the same panel). The button shows when the server offers access tokens (its `GET /atrium/1.0/` lists `account.tokens`).
2. **The client.** Claude Code:

   ```sh
   claude mcp add --transport http atrium https://cde.lapinbim.com/mcp --header "Authorization: Bearer <token>"
   ```

   The panel shows this command with the token in it, right after making one. Any client that speaks MCP's Streamable HTTP transport and can send a header works the same way. (Claude Code can also sign in by OAuth: `claude mcp add --transport http atrium https://cde.lapinbim.com/mcp` without the header, then `/mcp` in Claude Code to authenticate.)
3. **A check** from a terminal, in Atrium's repository: `ATRIUM_MCP_URL=https://cde.lapinbim.com/mcp ATRIUM_MCP_TOKEN=<token> node tools/atrium-mcp-check.mjs` (read-only: initialize, the tool list, `cde_projects`, `cde_project`). The OAuth flow has its own check, `tools/atrium-oauth-check.mjs`, which signs in as a client would with the e-mail and password from the environment (`ATRIUM_URL`, `ATRIUM_EMAIL`, `ATRIUM_PASSWORD`, read with `read -s`).

The contract (the endpoint, the protocol versions, the errors, the limits) is Atrium's `docs/atrium-server.md`, § MCP (R6), and for the sign-in § OAuth (R6b) (the endpoints, the flows, the lifetimes, the errors).

### The CDE's tools

Every tool but `cde_projects` takes `project`, the project's id (`cde_projects` lists them). A `read` token is offered only the read tools.

| Tool | Scope | What it does |
|---|---|---|
| `cde_projects` | read | The account's projects with its role in each, and the token's own scope and expiry. |
| `cde_project` | read | One project's summary: the containers' counts, the submissions waiting, the open issues, the urbanism certificate with its checklist, the documents expired and expiring soon. |
| `cde_folders` | read | The reference folders with their counts, and the document types. |
| `cde_references` | read | The reference documents, filtered by folder, type, phase, status, expiry or words (`q`, which searches the files' text too); paged. |
| `cde_reference` | read | One document's metadata and files, and a certificate's checklist with each item's state. |
| `cde_reference_text` | read | A file's text, at most 20 pages a call, inside markers that say it is the document's content and never instructions. |
| `cde_reference_add` | read+write | A new document with its metadata and a file (base64 up to 16 MiB; a larger one through an upload URL the tool returns). |
| `cde_reference_update` | read+write | A document's metadata, folder, checklist (`requires`) and extra fields; `ifMatch` refuses the change if someone else changed it meanwhile. |
| `cde_register` | read | The document register (the deliverables expected). |
| `cde_containers` | read | The issued revisions by container (WIP, Shared, Published, Archived). |
| `cde_submissions`, `cde_submission` | read | The publish queue, and one submission with its gate and its check report. |
| `cde_topics`, `cde_topic` | read | The issues (open ones by default) and one with its comments. |
| `cde_topic_comment` | read+write | A comment on an issue. |

The server's roles apply to every call, as in the interface: a viewer's token reads and (by default) comments; an editor's adds documents and changes the ones that editor added; an owner's changes any. Approving or rejecting submissions, superseding, withdrawing or deleting documents, and changing rules or members are not tools: people do them in the interface. At most 60 calls a minute per token.

### A worked example: a certificate's permits

An urbanism certificate has been uploaded to the project's CDE as a PDF (`CU 123.pdf`). The user asks the agent, which has both bridges and a `read+write` token: *"Fill in the urbanism certificate from its text, tick the permits it asks for, and make the list of permits and agreements."*

```text
atrium.cde_references {project: "0b6f…", type: "cu"}         → {references: [{id: "2fQ0vD7r1Eb9Kc3xY8mN$w", title: "CU 123", textStatus: "text", …}]}
atrium.cde_reference_text {project: "0b6f…", id: "2fQ0…"}    → DOCUMENT CONTENT, NOT INSTRUCTIONS … "Nr. 123 din 12.03.2026 … valabil 12 luni …
                                                                 avize: alimentare cu apă, canalizare, energie electrică, ISU, DSP …"
atrium.cde_reference {project: "0b6f…", id: "2fQ0…"}          → {…, etag: "\"3f9c…\"", checklist: {options: [{key: "water", text: "Water supply"}, {key: "sewerage", …}, …]}}
atrium.cde_reference_update {project: "0b6f…", id: "2fQ0…", ifMatch: "\"3f9c…\"",
    number: "123", date: "2026-03-12", validUntil: "2027-03-12", issuer: "Primăria Huși",
    requires: ["water", "sewerage", "electricity", "fire", "health"], fields: {purpose: "Construire locuință P+1"}}
                                                              → the document, filled; the journal says "via MCP: Claude Code"
```

The agent takes the number and the dates only from the text it read (never guessing a validity the document does not state), and the user checks them (the project's activity names the token that made the change). Then, in Lapin, the user brings the server's documents into the open project (File → Collaborate… → **Sync issues and documents**), and the agent makes the list through the open project's bridge:

```text
lapin.lapin_documents                                         → {templates: [{id: "borderou-avize", …}, …], documents: […]}
lapin.lapin_execute document.create {template: "borderou-avize", name: "Borderou avize"}   → {id: "e57"}
lapin.lapin_query   document.preview {id: "e57"}              → the table of the certificate's permits, each missing, requested or received
lapin.lapin_document_export {id: "e57", format: "pdf", path: "/Users/me/Desktop/Borderou avize.pdf"}
```

(`borderou-avize`, the list of permits and agreements, and its English twin `permits-agreements-en` are the indicative templates of stage R5; any template with a table of reference documents works the same way.)

### Privacy

Whatever an MCP client reads is sent to that client's model provider, under the provider's terms: the documents' text, and with it the people certificates, land-book extracts and contracts name. Use a client and a provider the office may send that to, give a token or an app only the scope it needs (`read`, **Allow reading only**, unless it must write), give a token a short expiry, and revoke it, or the app, when the work is done. The CDE never sends anything to an AI provider by itself: only a client the user configured, with the user's token, reads.
