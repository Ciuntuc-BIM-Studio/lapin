# CDE functions: plan

Asked and approved on 30.10.2026 (decision 180). The goal: a project that is issued from Lapin the way an office issues it under ISO 19650, without a server and without accounts — a project folder on disk (local, a network share, a SharePoint or OneDrive folder synced to the computer), the ISO 19650 containers in it, files named by the convention, each issue a revision with a status, a transmittal and a manifest, and the project's own version saved with it so the issue can be reopened and compared. Before an issue, the checks a drawing office does by eye: title blocks, legends, scales, revisions, names, and the model's basics.

Stages 1–3 are open, in the `lapin` edition (MIT). The direct SharePoint link through Microsoft Graph and a company's configurable rule sets are premium, later, in a private sibling repository, through hooks the open module leaves (`CdeHooks`, as `MepHooks` does for MEP).

## Decisions

- **No server.** The CDE is a folder. Whatever syncs it (OneDrive, SharePoint's sync client, a NAS) is the office's business; Lapin writes files. The folder's path is kept in the project (`cde.folder` on the IfcProject), so it travels with the file; a folder that is not there is a warning, never an error, until an issue is made.
- **ISO 19650 containers.** `WIP`, `Shared`, `Published`, `Archived` under the project folder, made on the first issue that needs them. An issue goes into the container the user chooses; the status code suggests it (S0 → WIP, S1–S7 → Shared, A, B and CR → Published).
- **Naming after ISO 19650-2** (the UK national annex's field order, the one most offices use): `Project-Originator-Volume-Level-Type-Role-Number`, e.g. `PRJ-ORG-ZZ-00-DR-A-0101`. Each field is upper-case letters and digits; the project code, the originator, the volume and the default level and role are set once in Manage → Project folder; a sheet's level comes from the storey its plans draw (`00` for the storey at ±0.00, `01` above, `B1` below, `ZZ` for several), its role from its discipline (architecture A, structure S, MEP M, civil C, else the project's default), its number from the digits of its sheet number (`A-101` → `0101`). The type is `DR` for a sheet, `M3` for the model, `IE` for the transmittal. The revision and the status follow the name after underscores (`…-0101_S2_P01.pdf`), so the name's seven fields stay parseable and the metadata is visible in a plain folder listing.
- **Revisions and status codes** as ISO 19650-2: `P01, P02…` preliminary, `C01, C02…` contractual; status `S0`–`S7`, `A1`–`A9`, `B1`–`B9`, `CR`. The next revision is proposed from the last issue (P02 after P01; a contractual issue starts at C01). The sheet's title block shows its revision and status, and a revision table over the title block lists the issues the sheet went out in.
- **An issue is a version.** The issue is recorded in the project (a `LapinIssue` entity: when, revision, status, container, the files with their SHA-256 and each sheet's drawing hash), then the project is saved as a version named after the issue (docs/versions.md), so it can be reopened, restored or compared. The drawing hash is what lets the next check say "the sheet changed since P01 but is still P01".
- **Checks before issuing.** A list of rules, each blocking or a warning, run from Manage → Check and before an issue; a blocking finding stops the issue, warnings can be overridden. Every finding points at something the user can click (a sheet, a view, an element). The rules are a service (`ICdeRule`): a module registers its own, and a premium module will add a company's rule sets.
- **Desktop first.** Issuing writes files, so it needs the desktop app (the browser build has no file system); the checks, the naming and the settings run anywhere.
- **Lapin's own property set for issue data** is `Lapin_Issue` (never `Pset_…`): the revision and status of a sheet, written on the sheet's title block as `revision` and `status`.

## Architecture

Everything lives in the platform (`core`), beside Sheets and Versions, because an issue needs what only the host's dispatcher reaches: the sheet PDFs, the IFC export (which takes the session), the project's file for the version.

- `engine/src/Platform/Lapin.Platform/Cde/CdeNaming.cs`: the convention (`Naming` record with the project's fields, `For(sheet)`, `Model()`, `Transmittal(n)`, `Validate`, `Parse`), the level code from storeys, the role from a discipline.
- `Cde/CdeRevisions.cs`: revision sequencing (`Next`, `IsValid`), the status codes with their labels, the container a status suggests.
- `Cde/CdeChecks.cs`: `ICdeRule`, `CdeFinding`, the built-in rules and the runner (`CdeChecks.Run`), `CdeHooks` (extra rules, a naming override) for a module in another repository.
- `Cde/CdeIssues.cs`: the `LapinIssue` entity (recorded by `cde.recordIssue`, listed by `cde.issues`), the last issue of a sheet.
- `Cde/CdeTransmittal.cs`: the transmittal as a PDF page (`PdfWriter`), as CSV, and the manifest JSON with SHA-256 per file.
- `Cde/Cde.cs`: the settings on the project (`cde.setFolder`, `cde.setNaming`, query `cde.settings`), the queries `cde.naming`, `cde.check`, `cde.issues`, the commands `cde.recordIssue`, `cde.deleteIssue`.
- `Lapin.Protocol/EngineDispatcher.cs`, method `cde.issue`: runs the checks (refuses on a blocking finding), takes the names, writes each sheet's PDF (and the set PDF, the IFC, the DXFs on request) into the container, hashes them, writes the transmittal (PDF and CSV) and the manifest, records the issue (`cde.recordIssue`, one undo step). The interface then saves the version (`project.saveVersion`, named after the issue), through the same path Manage → Versions uses, so the browser's bytes and an unsaved project are handled as there.
- `Sheets.cs`: the title block gains the revision, the status and who checked; a revision table over the title block from the issues; `Sheets.DrawingHash` (the views' pens on the paper, not the frame or the date) and `Sheets.Problems` (a view outside the frame or over the title block), shared with the checks.
- UI, `ui/src/modules/core/cde/`: `ProjectFolderDialog` (Manage → Project folder…: the folder, picked with the desktop's dialog, the containers, the naming fields with the name they make, the issues with Open folder), `IssueDialog` (Manage → Issue…: name, revision, status, container, the sheets, model and DXF, a note; the checks run first and are listed; blocking stops, warnings need "Issue anyway"), `CheckDialog` (Manage → Check: the findings grouped by rule, a click selects or opens), `revisions.ts` (the pure helpers, tested). The sheet's properties show Revision, Status and Phase. The desktop's `open_path` command opens a folder in the system's file manager.

## The rules of stage 1

Blocking: a title block field empty (number, title, drawn by); a view on a sheet without a scale; a view outside the frame or over the title block; a sheet changed since its last issue but still at that revision; a name that breaks the convention. Warnings: checked by, date and phase left empty (the date is printed as today's when empty), a revision left empty (Manage → Check only; an issue sets it); a legend missing on a sheet whose plans fill rooms by a colour scheme, or whose drawing has four or more fills; a plan, section or elevation on no sheet; a site plan without a north arrow; elements of the building classes on no storey, without a type, without a material; doors and windows without a tag; rooms without a number; `Pset_…Common` properties the project requires left empty (by default IsExternal on walls, slabs, roofs, doors and windows, LoadBearing on walls, slabs, columns and beams, FireRating on doors; `cde.setNaming {requiredProps}` changes the list).

## Stages

1. **Project folder, naming, checks, issues (done, 30.10.2026).** As above; tests `CdeTests` (naming, revisions, each rule both ways, the manifest and hashes, the CSV, the issue end to end in a temporary folder), `cde.test.ts` (the interface's helpers); the guide's page Project folder and issues in every language, scene `cde`.
2. **BCF topics in the folder.** BCF 2.1 and 3.0 files (`.bcfzip`) read from and written into the project folder: topics with their viewpoints, opened at their camera and with their components selected, answered from Lapin; a topic made from a selection and a view.
3. **PDF annotations read back.** The marks a reviewer puts on an issued PDF (comments, clouds, strikes) read from the file back into Lapin as remarks on the sheet, at their place, with who and when, closed from Lapin.
4. **SharePoint through Graph (premium).** The folder as a document library: sign-in, the containers as folders with their metadata columns (revision, status, suitability), issues uploaded directly, the transmittal as a library item; a company's rule sets (its naming, its required fields, its blocking rules) as a configuration the premium module loads, through `CdeHooks`.

## Open questions

1. The set PDF (all sheets in one file) is named with the model's volume and level and number `0000`; an office may want it per volume. The naming fields are the place to add a rule when one asks.
2. The level code takes the storey at ±0.00 as `00`; a project whose ground floor is not at ±0.00 names its storeys from the lowest. A per-storey code in the storey's properties would be the next step.
3. Whether to write a copy of the `.lapin` file itself into the container with the issue (the native model beside the IFC). Not done: the version in the project's own file is the record; the IFC is the exchange.
