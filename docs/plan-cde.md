# CDE functions: plan

Asked and approved on 30.10.2026 (decision 180). The goal: a project that is issued from Lapin the way an office issues it under ISO 19650, without a server and without accounts — a project folder on disk (local, a network share, a SharePoint or OneDrive folder synced to the computer), the ISO 19650 containers in it, files named by the convention, each issue a revision with a status, a transmittal and a manifest, and the project's own version saved with it so the issue can be reopened and compared. Before an issue, the checks a drawing office does by eye: title blocks, legends, scales, revisions, names, and the model's basics.

Stages 1–3 are open, in the `lapin` edition (MIT). The direct SharePoint link through Microsoft Graph and a company's configurable rule sets are premium, later, in a private sibling repository, through hooks the open module leaves (`CdeHooks`, as `MepHooks` does for MEP).

## Decisions

- **The project file holds the CDE; the folder is the exchange, and optional (decision 185, 31.10.2026).** Every issue's deliverables (the sheets' PDFs, the set, the transmittal PDF and CSV, the manifest, the DXFs) are kept in the `.lapin` under `issues/blobs/<sha256>`, content-addressed like the versions' blobs (identical bytes once across issues), listed by the issue's record; the IFC only on request (`keepModel`), its name and hash recorded either way. A project folder, when the desktop has one, receives a copy as before; without one the issue goes all the same, into the project file alone. An issue made earlier is published to a folder later, downloaded as one zip, or opened file by file from the project file. So the CDE works in the browser build too; only the project folder, publishing to it and scanning it are the desktop's.
- **No server.** The CDE is a folder. Whatever syncs it (OneDrive, SharePoint's sync client, a NAS) is the office's business; Lapin writes files. The folder's path is kept in the project (`cde.folder` on the IfcProject), so it travels with the file; a folder that is not there is a warning, never an error, until an issue is made.
- **ISO 19650 containers.** `WIP`, `Shared`, `Published`, `Archived` under the project folder, made on the first issue that needs them. An issue goes into the container the user chooses; the status code suggests it (S0 → WIP, S1–S7 → Shared, A, B and CR → Published).
- **Naming after ISO 19650-2** (the UK national annex's field order, the one most offices use): `Project-Originator-Volume-Level-Type-Role-Number`, e.g. `PRJ-ORG-ZZ-00-DR-A-0101`. Each field is upper-case letters and digits; the project code, the originator, the volume and the default level and role are set once in Manage → Project folder; a sheet's level comes from the storey its plans draw (`00` for the storey at ±0.00, `01` above, `B1` below, `ZZ` for several), its role from its discipline (architecture A, structure S, MEP M, civil C, else the project's default), its number from the digits of its sheet number (`A-101` → `0101`). The type is `DR` for a sheet, `M3` for the model, `IE` for the transmittal. The revision and the status follow the name after underscores (`…-0101_S2_P01.pdf`), so the name's seven fields stay parseable and the metadata is visible in a plain folder listing.
- **Revisions and status codes** as ISO 19650-2: `P01, P02…` preliminary, `C01, C02…` contractual; status `S0`–`S7`, `A1`–`A9`, `B1`–`B9`, `CR`. The next revision is proposed from the last issue (P02 after P01; a contractual issue starts at C01). The sheet's title block shows its revision and status, and a revision table over the title block lists the issues the sheet went out in.
- **An issue is a version.** The issue is recorded in the project (a `LapinIssue` entity: when, revision, status, container, the files with their SHA-256 and each sheet's drawing hash), then the project is saved as a version named after the issue (docs/versions.md), so it can be reopened, restored or compared. The drawing hash is what lets the next check say "the sheet changed since P01 but is still P01".
- **Checks before issuing.** A list of rules, each blocking or a warning, run from Manage → Check and before an issue; a blocking finding stops the issue, warnings can be overridden. Every finding points at something the user can click (a sheet, a view, an element). The rules are a service (`ICdeRule`): a module registers its own, and a premium module will add a company's rule sets.
- ~~**Desktop first.**~~ Since decision 185 issuing runs anywhere the project file is (the desktop, the browser); the project folder alone is the desktop's.
- **Lapin's own property set for issue data** is `Lapin_Issue` (never `Pset_…`): the revision and status of a sheet, written on the sheet's title block as `revision` and `status`.

## Architecture

Everything lives in the platform (`core`), beside Sheets and Versions, because an issue needs what only the host's dispatcher reaches: the sheet PDFs, the IFC export (which takes the session), the project's file for the version.

- `engine/src/Platform/Lapin.Platform/Cde/CdeNaming.cs`: the convention (`Naming` record with the project's fields, `For(sheet)`, `Model()`, `Transmittal(n)`, `Validate`, `Parse`), the level code from storeys, the role from a discipline.
- `Cde/CdeRevisions.cs`: revision sequencing (`Next`, `IsValid`), the status codes with their labels, the container a status suggests.
- `Cde/CdeChecks.cs`: `ICdeRule`, `CdeFinding`, the built-in rules and the runner (`CdeChecks.Run`), `CdeHooks` (extra rules, a naming override) for a module in another repository.
- `Cde/CdeIssues.cs`: the `LapinIssue` entity (recorded by `cde.recordIssue`, listed by `cde.issues`), the last issue of a sheet.
- `Cde/CdeTransmittal.cs`: the transmittal as a PDF page (`PdfWriter`), as CSV, and the manifest JSON with SHA-256 per file.
- `Cde/Cde.cs`: the settings on the project (`cde.setFolder`, `cde.setNaming`, query `cde.settings`), the queries `cde.naming`, `cde.check`, `cde.issues`, the commands `cde.recordIssue`, `cde.deleteIssue`.
- `Cde/Remarks/` (stage 2): `BcfModel.cs` (the BCF subset as records, and as the remark's JSON attributes), `BcfReader.cs` (2.1 and 3.0, lenient, by local names), `BcfWriter.cs` (2.1 by default, 3.0 on request, `XmlWriter` in the schemas' element order, `ZipArchive`), `Remarks.cs` (the `LapinRemark` entity, id = topic GUID as a GlobalId; `remarks.create`, `remarks.update`, `remarks.comment`, `remarks.addViewpoint`, `remarks.delete`; queries `remarks.list` without the snapshots and `remarks.snapshot`; `Import` merging by GUID and `Export` of all, the open ones or ids). The dispatcher's `project.importBcf` and `project.exportBcf` carry the bytes (a guest may import by bytes, never by path). `Session.Dto` leaves the snapshots out of the node sent to the interface.
- `Lapin.Protocol/EngineDispatcher.cs`, method `cde.issue` (`CdeIssue.Run`): runs the checks (refuses on a blocking finding), takes the names, makes each sheet's PDF printed as issued (`Sheets.Issuing`: the issue's revision and status in the title block, its row in the revision table), the set PDF, the IFC and the DXFs on request, hashes them, makes the transmittal (PDF and CSV) and the manifest, keeps every file in the project's store (`PackageIssues`, the IFC only with `keepModel`) and, when the project has a folder on this computer (`toFolder`, never in the browser), writes them into the container too; records the issue (`cde.recordIssue`, one undo step) with the number of the version it is about to save (`PackageVersions.NextNumber`), then saves that version (`ProjectFiles.SaveVersion`, named after the issue) in the same call, so the project is clean after (`bytes: true`: the package comes back to the browser). An unsaved project on the desktop keeps the files in memory until its first save, without a version (the interface asks for Save as first, as Versions does). `cde.issueFile` (one file: to a path, to the temporary folder to open it, or as bytes), `cde.issueZip`, `cde.publishIssue` (the project folder's container, or any folder `flat`, dated as issued so the scan does not take them for reviewed), `cde.missing` (hashes a record keeps that the file does not hold); in the platform `cde.dropIssueFiles` (one undo step) and the query `cde.storage`.
- `Lapin.Package/PackageIssues.cs`: the store of the issues' files — those read with the package (`issues/blobs/`), those made since in memory; `LapinPackage.Write` writes the hashes the records keep (`IssueFiles`) and `issues/index.json` (the records repeated for whoever opens the zip without Lapin).
- `Sheets.cs`: the title block gains the revision, the status and who checked; a revision table over the title block from the issues; `Sheets.DrawingHash` (the views' pens on the paper, not the frame or the date) and `Sheets.Problems` (a view outside the frame or over the title block), shared with the checks.
- UI, `ui/src/modules/core/cde/`: `ProjectFolderDialog` (Manage → Project folder…: the folder, picked with the desktop's dialog, the containers, the naming fields with the name they make, the issues with Open folder), `IssueDialog` (Manage → Issue…: name, revision, status, container, the sheets, model and DXF, a note; the checks run first and are listed; blocking stops, warnings need "Issue anyway"), `CheckDialog` (Manage → Check: the findings grouped by rule, a click selects or opens), `revisions.ts` (the pure helpers, tested). The sheet's properties show Revision, Status and Phase. The desktop's `open_path` command opens a folder in the system's file manager.

## The rules of stage 1

Blocking: a title block field empty (number, title, drawn by); a view on a sheet without a scale; a view outside the frame or over the title block; a sheet changed since its last issue but still at that revision; a name that breaks the convention. Warnings: checked by, date and phase left empty (the date is printed as today's when empty), a revision left empty (Manage → Check only; an issue sets it); a legend missing on a sheet whose plans fill rooms by a colour scheme, or whose drawing has four or more fills; a plan, section or elevation on no sheet; a site plan without a north arrow; elements of the building classes on no storey, without a type, without a material; doors and windows without a tag; rooms without a number; `Pset_…Common` properties the project requires left empty (by default IsExternal on walls, slabs, roofs, doors and windows, LoadBearing on walls, slabs, columns and beams, FireRating on doors; `cde.setNaming {requiredProps}` changes the list).

## Stages

1. **Project folder, naming, checks, issues (done, 30.10.2026).** As above; tests `CdeTests` (naming, revisions, each rule both ways, the manifest and hashes, the CSV, the issue end to end in a temporary folder), `cde.test.ts` (the interface's helpers); the guide's page Project folder and issues in every language, scene `cde`.
2. **BCF remarks on the model (done, 30.10.2026).** Remarks kept in the project as `LapinRemark` entities (resources, never in the IFC), each a BCF topic with its comments and viewpoints; BCF 2.1 (`.bcfzip`) and 3.0 (`.bcf`) read, 2.1 written by default and 3.0 on request, with no dependency (`Lapin.Platform/Cde/Remarks`: `BcfModel`, `BcfReader`, `BcfWriter`, `Remarks`; `project.importBcf` and `project.exportBcf` in the dispatcher, by path or by bytes, so the browser build has them too). A remark's entity id is its topic GUID in IFC's 22-character form, so a round trip through BIMcollab, Solibri or Revit updates the same remark (the file's fields win, comments and viewpoints merge by GUID). Manage → Remarks… (`ui/src/modules/core/remarks/`): the list with filters, a remark's fields, snapshot and comments, a new remark from the 3D view with a snapshot taken from the canvas, Show in 3D (camera, selection by GlobalId, clipping planes as the section box; `bcfCamera.ts` converts both ways, tested), Import BCF…, Export all / open / selected. Hidden components (Visibility exceptions) and lines are kept and written back but not shown: Lapin's 3D has no per-element hiding. Watching the folder for new BCF files is out of scope. Tests `RemarksTests` (10), `bcfCamera.test.ts` (10), `remarks.test.ts` (5); the guide's Remarks section in every language, scene `remarks`.
3. **PDF annotations read back.** The marks a reviewer puts on an issued PDF (comments, clouds, strikes) read from the file back into Lapin as remarks on the sheet, at their place, with who and when, closed from Lapin.
2. **BCF topics in the folder.** BCF 2.1 and 3.0 files (`.bcfzip`) read from and written into the project folder: topics with their viewpoints, opened at their camera and with their components selected, answered from Lapin; a topic made from a selection and a view.
3. **PDF annotations read back (done, 30.10.2026).** The marks a reviewer puts on an issued PDF (comments, clouds, strikes) read from the file back into Lapin as remarks on the sheet, at their place, with who and when, closed from Lapin. `Cde/PdfRemarks/`: a PDF reader of Lapin's own, no dependency — `PdfDocument` (xref tables and xref streams, object streams, incremental updates through /Prev and /XRefStm, FlateDecode with the PNG predictors, a scan of the file for "n g obj" when the chain is broken, the newest definition winning), `PdfText` (PDFDocEncoding, UTF-16BE and UTF-8 with their marks, escapes, hex strings, PDF dates), `PdfAnnotations` (the markup annotations of each page with their geometry, text, author, dates, colour, /IRT threads and review states; popups, links, widgets and hidden ones skipped), `PdfPageMap` (the page onto the sheet's paper: CropBox within MediaBox, /Rotate, a page of another size scaled with a warning) — and `CdeRemarks`: the `LapinSheetRemark` entity on the sheet (kind, box and paths in paper mm, text, author, date, status open/resolved/closed, the source file, revision, page and annotation so a re-read updates rather than duplicates, the replies), the sheet matched by the project's issue record, the folder's `lapin-issue/1` manifest, the file name's convention, or the user's choice (a set's pages to its sheets in order); `cde.importRemarks`, `cde.setRemarkStatus`, `cde.deleteRemarks`, queries `cde.remarks` and `cde.pdfRemarks` (from bytes). The host's `cde.readPdf` (a path, or bytes from a browser; the manifests beside the file) and `cde.scanRemarks` (Shared and Published: the issued PDFs changed since their issue, read since or not), refused to guests. UI `ui/src/modules/core/cde/pdfRemarks/`: Manage → Remarks (read a PDF, scan the folder, the list by sheet with a status filter, a click opens the sheet with the remark in front, resolve, close, reopen, delete), the overlay in the sheet view (outline in the review colour, a marker with the author's initials, the text in a tooltip and on a card, a toggle in the toolbar) and the count of open remarks beside the sheet in the project browser; an overlay for the screen alone, a sheet prints without it. Tests `CdePdfRemarksTests` (9: the incremental update, the xref stream through the predictor, text and dates, the transform with /Rotate and another size, the writer's own PDF read back, the matching, broken files, the host by path and the scan), `remarks.test.ts` (5); the guide's section in every language, scene `cde-remarks`. Not done: replies written from Lapin into the PDF (Lapin never writes into an issued file), annotations with no geometry the reader knows (3D, rich media, sound), a BCF topic from a remark (stage 2's).
4. **SharePoint through Graph (premium).** The folder as a document library: sign-in, the containers as folders with their metadata columns (revision, status, suitability), issues uploaded directly, the transmittal as a library item; a company's rule sets (its naming, its required fields, its blocking rules) as a configuration the premium module loads, through `CdeHooks`.

## Stage 1b: the CDE in the project file (decision 185, done, 31.10.2026)

Asked by the user after filming the CDE: the `.lapin` holds the issues' history and deliverables, the folder becomes the optional exchange, the CDE works on the web. Done as described under Decisions and Architecture: `issues/blobs/<sha256>` and `issues/index.json` in the package (format 3 unchanged: an older file without `issues/` opens as before, an older Lapin skips the folder), the IFC kept on request, Publish to folder…, Download as zip, open a file from the project, the size the issues take (Manage → Project folder, per issue and in all) and Delete stored files (the record and hashes stay). A reviewer's PDF renamed on the way is matched by the issued bytes it begins with (an incremental save keeps them). Five fixes found while filming: a disabled `.btn` looks it in every theme; the Issue dialog shows the issue made, by its own names, until closed or New issue; the open-remarks count counts open only (not resolved, not closed); the project is saved after an issue (record and version in one call); an empty title block project field shows the project's name (the IfcProject's own name when given, else the file's name). And a sixth: an issued sheet now prints its own revision and status (before, the PDF carried the previous ones, the record being written after the printing). Tests `CdeTests` (22, of which `CdeStoreTests` 7), `cde.test.ts` (8), `remarks.test.ts` (5); the guide's page in every language with the pictures `cde-issued` and `cde-issues`.

What the deduplication buys in practice: a sheet's PDF differs from one issue to the next (its title block and revision table carry the issue), so identical bytes come from re-issuing an unchanged file (an issue undone and made again, a record carried forward, a transmittal CSV that happens to be equal); the store costs nothing extra in those cases, and an old issue's files can be let go.

## Open questions

1. The set PDF (all sheets in one file) is named with the model's volume and level and number `0000`; an office may want it per volume. The naming fields are the place to add a rule when one asks.
2. The level code takes the storey at ±0.00 as `00`; a project whose ground floor is not at ±0.00 names its storeys from the lowest. A per-storey code in the storey's properties would be the next step.
3. Whether to write a copy of the `.lapin` file itself into the container with the issue (the native model beside the IFC). Not done: the version in the project's own file is the record; the IFC is the exchange.
4. A BCF viewpoint's hidden components and its lines are kept on the remark and written back, but the 3D view does not hide elements per element yet; a BCF camera's roll is lost (Lapin's camera keeps Z up). Clipping planes off the box's axes are kept but not shown. Watching the project folder for BCF files dropped in it (and the BCF-API of a server) is for later, with the premium SharePoint stage.
